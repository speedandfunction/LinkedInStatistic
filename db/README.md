# `db/` — the database layer

Сьогодні корпус живе як JSON у **публічному** репозиторії: 720 іменних файлів
людей, дослівні тексти коментарів, і щотижневі знімки акаунтів, які LinkedIn
ніколи не віддасть назад — він показує тільки *поточні* значення. Тому імпорт
мусить бути правильний з першого разу: тут немає «перезбираємо ще раз».

Це шар, що переносить корпус у Postgres так, щоб коли приїдуть креденшали й
права на Grafana, перемикання було механічним, а не переписуванням.

```
db/schema.sql           DDL: схеми li + dash, таблиці, індекси, в'юхи, merge-функції, п'ять ролей
db/apply-schema.mjs     накотити schema.sql через драйвер, атомарно (керований Postgres)
db/import.mjs           JSON з диска -> база (власник АБО li_sync)
db/export.mjs           з бази -> той самий stats.json / page-stats.json; нічого не пише
db/verify.mjs           parity: зібрати обидва боки і подіфати поле за полем
db/ping.mjs             keep-alive: одне читання роллю li_sync, щоб Supabase не приспав проєкт між понеділками
db/backup.sh            pg_dump схем li + dash роллю li_backup; у лог — лише лічильники
db/restore-drill.sh     відновити дамп у тимчасову базу і звірити з джерелом
db/pg-env.mjs           DSN з env -> PG*-змінні для psql/pg_dump (+ TLS, + redactor для stderr)
db/docker-bin/          локальні підміни psql/pg_dump через контейнер li-pg (у CI не потрібні)
db/safe-log.mjs         що можна друкувати в публічний лог, а що ні
db/pg-config.mjs        конфіг підключення для Node (TLS із закріпленим CA) + resolveDsn
db/merge-rules.mjs      як згортається батч перед відправкою (поруч із рядками merge.py)
db/test-merge-rules.mjs звірка трьох merge-правил із фактичною поведінкою merge.py
db/test-roles.mjs       права п'яти ролей ДІЄЮ, включно зі справжнім імпортом від li_sync
db/fixture-icp.mjs      синтетичний корпус із ICP/VIP + паритет на ньому
db/package.json         Node + pg
```

## Dual-write: що це і що обіцяє `db/`

JSON у git лишається джерелом правди. Після того як дані лягли в `main`, ті самі
дані синхронізуються в Postgres, і 2–3 тижні обидва сховища порівнюються
автоматично. Ворота якості — git-PR: неповний тиждень сидить у відкритому PR, у
`main` його немає, отже він ніколи не синхронізується. Те, що є в `main`, —
опубліковане за визначенням, тому синк має право публікувати те, що імпортує.

Контракт із CI (усі команди беруть DSN **з env, ніколи з argv**):

| команда | роль | вихід |
|---|---|---|
| `LI_DSN=<sync> node db/import.mjs --publish` | `li_sync` | `0` ок; останній рядок stdout — завжди `-- N rows written` (і для `N=0`). `1` — впало й відкотилось, `2` — відмова (`--reset` не тією роллю, порожній `LI_DSN` у CI) |
| `LI_DSN=<sync> node db/verify.mjs` | `li_sync` | `0` байт-в-байт · `1` **різниця** (шляхи + хеші; фід, що є лише з одного боку, — теж різниця, `[feed-absent]`) · `2` перевірка **не змогла відбутися** (база лежить, впав build-скрипт, 0 фідів). Завжди друкує `-- N feed(s) compared, M differ`: CI звіряє `N` з кількістю фідів, які публікує `main`, і без цього `0` не вважає за `ok` |
| `LI_DSN=<sync> node db/ping.mjs` | `li_sync` | `0` база відповіла (`ping ok — N import run(s) on record`) · `1` не відповіла (лише форма помилки). Щоденний keep-alive з `linkedin-session-check.yml` |
| `LI_BACKUP_DSN=<backup> db/backup.sh <out.sql>` | `li_backup` | `0` ок · `2` виклик · `3` `pg_dump` молодший за сервер · `4` база недосяжна / `pg_dump` впав · `5` дамп порожній або не збігається з базою |

`verify.mjs` раніше виходив з `1` і на необроблений виняток — тобто «сховища
розійшлися» і «ніхто не подивився» були одним кодом. Тепер це `1` і `2`.

Залежності: `npm ci --prefix db`. Секрети (створює оператор): `LI_SYNC_DATABASE_URL`,
`LI_BACKUP_DATABASE_URL`, `LI_BACKUP_DEPLOY_KEY`.

Що `db/` гарантує зі свого боку:

* **Жодної ролі власника в CI.** `li_sync` може відтворити `main` і більше нічого
  (див. «Ролі»); `li_backup` лише читає.
* **Жодних персональних даних у лозі.** Помилка друкується *формою* — SQLSTATE,
  таблиця, обмеження, функція — а не текстом: `detail` у Postgres — це сам рядок
  («Failing row contains …»), повідомлення про підключення несе хост і
  користувача, `SyntaxError` у Node цитує шматок файла, а файли кеша профілів
  названі слагом людини. Усе це вирізає `safe-log.mjs`; повний текст — лише з
  `--show-values`, локально. `pg-env.mjs` так само чистить stderr `psql`/`pg_dump`.
* **Порожній секрет — не localhost.** Якщо `LI_DSN` порожній, а довкола CI
  (`GITHUB_ACTIONS`/`CI`), скрипти виходять із `2` і пишуть «LI_DSN is not set», а
  не мовчки йдуть на локальний дефолт і падають з `ECONNREFUSED`.
* **Один імпортер за раз** (`pg_advisory_xact_lock`): тижневий воркфлоу і ручний
  `pages-deploy` можуть синхронізувати той самий мердж — другий стане ідемпотентним
  повтором, а не колізією на унікальному індексі гейту.

## Дві схеми

| | |
|---|---|
| **`li`** | факти. Що скрапер побачив і коли. Нічого похідного. Grafana сюди не має доступу взагалі. |
| **`dash`** | опублікована поверхня читання. Кожна в'юха джойниться до гейту й показує **тільки опубліковані тижні**. |

Правила, які не обговорюються:

* **ISO-тиждень — це `date`** (понеділок), ніколи не рядок.
* **Відсотки й рейти — `numeric`**, ніколи `double precision`. У корпусі є `0.41`
  і `50.0`; float8 віддав би `0.41000000000000003` і зробив би parity-діф
  нечитабельним.
* **Кожен рядок несе `run_id`** — «який скрап це поклав» відповідається без
  `git blame`.
* Ролі створюються **без паролів** — їх ставить оператор окремо (див. нижче).

## Запустити локально

Потрібен Postgres 16. Локально він уже крутиться в Docker як `li-pg`:

```
postgresql://postgres:devpw@localhost:55432/linkedin
```

`psql` на хості немає — усе через контейнер.

```bash
# 1. накотити схему (дропає li і dash та створює наново)
docker exec -i li-pg psql -U postgres -d linkedin -v ON_ERROR_STOP=1 < db/schema.sql

# 2. поставити залежності
cd db && npm install && cd ..

# 3. імпортувати реальні дані й опублікувати тижні цього корпусу
node db/import.mjs --reset --publish      # --reset — лише власник

# 4. перевірити паритет
node db/verify.mjs

# 5. звірити merge-правила з merge.py і прогнати ICP/VIP-фікстуру
node db/test-merge-rules.mjs
node db/fixture-icp.mjs

# 6. права ролей ДІЄЮ (див. «Ролі»): справжній імпорт від li_sync у тимчасовій базі,
#    відмови на все зайве, li_backup читає все і нічого не пише, годинник не тече
node db/test-roles.mjs

# 7. резервна копія і навчальне відновлення (psql/pg_dump — з контейнера)
export PATH="$PWD/db/docker-bin:$PATH"
LI_BACKUP_DSN=... db/backup.sh /tmp/li-backup/li.sql
LI_DRILL_DSN=postgresql://postgres:devpw@localhost:55432/postgres \
LI_BACKUP_DSN=... db/restore-drill.sh /tmp/li-backup/li.sql --verify
```

DSN береться з `LI_DSN`; `--dsn` лишився для локального термінала (argv видно в
`ps` і в лозі — там, де пароль справжній, ним не користуються); далі — локальний
дефолт, який у CI вимкнений.

### `import.mjs`

```
LI_DSN=<url> node db/import.mjs [--repo <path>] [--reset] [--publish] [--quiet]
                                [--decided-by <мітка>] [--show-values]
```

**Хто його запускає.** Будь-яка роль з `EXECUTE` на merge-функції: власник або
`li_sync`. Раніше імпортер вимагав власника у чотирьох місцях — `li.set_scoring`,
`li.set_vip`, `li.replace_page` і прямий `UPDATE li.week_publication` під
`--publish`. Перші три тепер видані `li_sync`, а `UPDATE` замінений функцією
`li.publish_run()` (див. «Гейт публікації»). Перевірено кожен `insert … on conflict`,
який імпортер видає сам:

| пряма вставка | конфлікт | чому так |
|---|---|---|
| `li.import_run` | немає | `run_id` — свіжий UUID |
| `li.engagement_event` | `DO NOTHING` | це і є правило: `merge.py:272`, `if event_id in events: continue`. `DO UPDATE` тут був би помилкою, а не покращенням |
| `li.author` | ~~`DO NOTHING`~~ → `li.upsert_author()` | `profiles.json` — конфіг, тобто вид **ЗАМІНА**, а не append. З `DO NOTHING` перейменована людина чи зсунутий `posts_cutoff` не доїжджали до бази ніколи; чесне виправлення — `DO UPDATE` — вимагає `UPDATE`, якого в CI-ролі немає. Тому definer-функція, з тим самим `is distinct from`-запобіжником. Авторів вона не видаляє |

`--reset` очищає всі таблиці `li` перед імпортом. Це єдиний деструктивний флаг —
прапорець **власника**. Роль без `TRUNCATE` (`li_sync`, `li_writer`) дістає
відмову **до** будь-якої зміни, з кодом `2` і зрозумілим текстом, а не голе
`permission denied for table author`.

`--publish` переводить тижні **цього прогону** з `pending` у `published` через
`li.publish_run()`. **Без нього в `dash` не видно нічого**: імпорт лише *просить*
публікацію (`li.request_week()`). Після публікації імпортер перевіряє
пост-умову в тій самій транзакції — кожен прочитаний тиждень мусить бути видимим;
якщо ні, прогін падає і відкочується, а не комітить корпус із дірками.
`decided_by` — мітка (`--decided-by`, `LI_DECIDED_BY`, у Actions — номер прогону)
плюс `session_user`, дописаний самою функцією: мітка не може видати себе за логін.

Імпорт **ідемпотентний у строгому сенсі**: другий прогін по *тих самих* даних не
переписує жодного кортежа (кожен `DO UPDATE` має `where ... is distinct from`).
Це **не** те саме, що «ігнорує зміни»: якщо тиждень перескрапили, нові числа
лягають — див. розділ про merge-правила.

### `export.mjs`

```
node db/export.mjs --author peter --out /tmp/li-export/peter/stats.json
node db/export.mjs --page          --out /tmp/li-export/page-stats.json
node db/export.mjs --all           --out-dir /tmp/li-export/
```

`--out` / `--out-dir` **обов'язкові**, дефолтів немає. У виводі — 628 іменованих
людей із хедлайнами й посиланнями на профілі, тобто рівно те, що ця міграція
виносить із публічного репо. Дефолт на кшталт `peter-stats.json` писав би це в
корінь репозиторію, звідки один `git add .` робить дані публічними назавжди.
Пишіть **поза деревом**. У `.gitignore` про всяк випадок додані `pages-dist-db/`,
`/page-stats.json`, `/*-stats.json`, `out/`.

**Нічого не пише.** Одне з'єднання, одна транзакція `REPEATABLE READ READ ONLY`
(один знімок на весь експорт, і «не пише» гарантує сервер, а не коментар); пін
годинника — всередині неї, див. «Годинник».

Читає **виключно `dash`** — ту саму поверхню, яку отримує Grafana, — і окремий фід
(`--author`, `--page`) справді знімається роллю `grafana_ro`, байт-в-байт з тим, що
дає `li_sync`. Лише `--all` і `verify.mjs` беруть перелік авторів з `li.author`, тож
їм потрібен `SELECT` на `li` (у `li_sync` він є). (Проба «чи не запінений глобальний рядок» спершу
питала `has_table_privilege('li.dash_config', …)` — а для ролі без `USAGE` на `li`
саме *називання* цієї таблиці вже `42501`, тож експорт від `grafana_ro` падав на
відкритті сесії. Тепер спершу `has_schema_privilege`; `test-roles.mjs` відкриває
сесію експортера від `grafana_ro` і перевіряє, що пін доходить до в'юх.) Якщо звідси
виходять правильні байти, то датасорсу, наведеному на `dash`, вистачає всього, а
`li` може лишатися приватною.

### `verify.mjs`

```
node db/verify.mjs [--now <iso>] [--max 40] [--keep]
                   [--repo <dir>] [--no-page] [--show-values]
```

Збирає фіди двічі — раз наявними `.github/scripts` з JSON на диску, раз із бази —
і діфає. Exit `0` = байт-в-байт, `1` = різниця, `2` = перевірка не відбулась.
Працює від `li_sync` і **нічого не лишає по собі** в базі.

**Які саме фіди.** Об'єднання двох списків: того, що JSON-бік **публікує** (кожна
тека `dashboards/li-stats/<author>/` з `account.json` — те саме правило, що в
`build-pages.mjs`), і того, що **є в базі** (`li.author`). Раніше список брався лише з
бази, і «ok» міг бути порожнім: автора видалили з `li.author` (або тека автора є на
Pages, а в `profiles.json` його немає, тож імпортер його не бачив) — і такий фід
просто не потрапляв у цикл, а перевірка проходила. Тепер фід, який є лише з одного
боку, — це `DIFF … 1 difference(s)` зі шляхом `<author> [feed-absent]`, exit `1`.
Наприкінці завжди друкується `-- N feed(s) compared, M differ`; `db-ci.mjs` рахує
очікувану кількість сам, з чекауту, і якщо `N` менше — стан `incomplete`, не `ok`.

**Різниця друкується шляхом і формою, а не значенням**: репозиторій публічний,
логи CI читає будь-хто, а значення тут — імена, хедлайни й URL сторонніх людей.
Для кожного розходження виводиться тип, довжина і `sha1[:8]` — два різні хеші на
одному шляху вже кажуть, що значення різні. `--show-values` друкує текст і
призначений лише для локального термінала.

`--repo` наводить **обидва боки** на інший корпус (фікстура), `--no-page` пропускає
фід сторінки компанії, якого у фікстури немає.

## Керований Postgres (Supabase)

Бойова база — Supabase, проєкт `linkedin-stats`, регіон `eu-central-1`. Три речі там
інакші, ніж у локальному контейнері, і кожна вже коштувала одного падіння:

**Підключення — лише Session pooler.** Пряме з'єднання Supabase працює тільки по IPv6.
Хост `aws-0-eu-central-1.pooler.supabase.com:5432`, користувач у форматі
`<роль>.<код-проєкту>`. Transaction pooler не годиться: там не працюють prepared statements.

**TLS перевіряється повністю.** Пулер підписаний власним коренем Supabase, якого немає у
сховищі Node, а `pg` трактує `sslmode=require` як `verify-full` — голий рядок підключення
падає з `SELF_SIGNED_CERT_IN_CHAIN`. Вимикати перевірку не можна; натомість корінь лежить у
`certs/supabase-root-2021.crt`, а всі скрипти будують конфіг через `pg-config.mjs`.
Сертифікат публічний (не секрет), узятий з офіційного бакета Supabase, його SHA-256 звірено з
коренем, який пред'являє сервер. Дійсний до 2031-04-26.

**`postgres` там не суперкористувач.** `rolsuper = false`, `rolcreaterole = true`. З PG16
творець ролі отримує на неї ADMIN OPTION, але не право `SET ROLE`, а `ALTER ... OWNER TO`
вимагає саме його — перша версія `schema.sql` падала посередині з
`must be able to SET ROLE "li_owner"`. Тепер файл спершу робить `grant li_owner to current_user`.
Відтворюється локально роллю з `createrole` без `superuser`.

```bash
# DSN береться з env, щоб пароль не світився в командному рядку і в `ps`
export LI_DSN="$LI_DATABASE_URL"

node db/apply-schema.mjs            # атомарно; відмовить, якщо в базі вже є тижневі зрізи (--force)
node db/import.mjs --publish
node db/verify.mjs                  # побайтова звірка проти бойової бази
```

### Викотити dual-write на бойову базу (оператор, один раз)

`schema.sql` починається з `DROP SCHEMA … CASCADE` і окремої міграції немає —
свідомо: на цьому етапі база є **похідною копією** JSON, у ній немає нічого, чого
не відтворить `import.mjs`. Тому викочування — це «перенакотити й переімпортувати».
Між двома транзакціями `dash` хвилину порожній.

```bash
export LI_DSN="$LI_DATABASE_URL"           # власник (postgres.<ref>)
node db/apply-schema.mjs --force           # нові функції, ролі li_sync + li_backup, сесійний годинник
node db/import.mjs --publish
node db/verify.mjs
```

Якщо перенакочувати прямо зараз не з руки, а **годинник уже заморожений** старим
`verify.mjs` — розморозити його можна одним рядком від власника:
`update li.dash_config set as_of = null;`

Потім паролі двом новим ролям — SCRAM-верифікатором, як і решті, — і секрети:

```sql
ALTER ROLE li_sync   WITH LOGIN PASSWORD 'SCRAM-SHA-256$…';
ALTER ROLE li_backup WITH LOGIN PASSWORD 'SCRAM-SHA-256$…';
```

```
LI_SYNC_DATABASE_URL    postgresql://li_sync.<ref>:…@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
LI_BACKUP_DATABASE_URL  postgresql://li_backup.<ref>:…@aws-0-eu-central-1.pooler.supabase.com:5432/postgres
```

І перевірити ролі справжнім входом. Частина B тесту створює тимчасову базу — на
Supabase це може бути недоступно, тоді `--no-scratch` (частина B уже прогнана
локально, з тими самими ролями і не-суперкористувачем-власником):

```bash
LI_SYNC_DSN=… LI_BACKUP_DSN=… LI_GRAFANA_RO_DSN=… LI_WRITER_DSN=… \
  node db/test-roles.mjs --no-scratch
```

`apply-schema.mjs` існує, бо `psql -f` до Supabase не дістає і не є атомарним: з
`ON_ERROR_STOP` він лише зупиняється, лишаючи все виконане до помилки закоміченим.

Паролі ролей `li_writer` і `grafana_ro` задаються SCRAM-верифікатором, а не відкритим
текстом, щоб пароль не осів у журналі сервера. На безкоштовному тарифі **резервних копій
немає**, а проєкт **засинає після 7 днів без активності** і вмикається лише вручну.

## Годинник

`build-stats-json.mjs` читає настінний годинник рівно у двох місцях, і обидва
**змінюють вивід**:

| місце | що псує |
|---|---|
| `currentMonthUTC()` в `zeroFillMonths()` (рядок ~159) | хвіст `posts_per_month` і `comments_per_month` — скільки порожніх місяців дописати |
| `currentWeekMonday` в блоці engagement (рядок ~323) | який тиждень вважається `last_week`, а отже `engagement_score_totals[0]` і `score_last_week` у кожного |

Тому до скрипта доданий `--now <iso>`, а в'юхи читають годинник через
`li.as_of()`. `verify.mjs` пінить обидва боки на один інстант. Без цього прогін,
що переліз через опівніч UTC, показав би різницю, якої немає.

### Пін живе в одній транзакції — і це виправлення бойового бага

Перша версія тримала пін у таблиці: `export.mjs` робив
`update li.dash_config set as_of = $1` і **ніколи не скидав**. `dash`-в'юхи читають
цей рядок через `li.as_of()`, тож одна перевірка паритету заморожувала «зараз» для
**кожного** читача спільної бойової бази — Grafana включно — доки хтось не помітить.
Глобальний, тихий, постійний побічний ефект перевірки, яка мала лише читати.

Тепер:

* `li.as_of()` = `coalesce(` GUC `li.as_of` `,` рядок `li.dash_config` `, now())`.
* `export.mjs` ставить GUC через `set_config('li.as_of', $1, true)` — **локально для
  транзакції** — всередині власної `READ ONLY`-транзакції. Не `SET` на сесію:
  за session-пулером Supabase бекенд після нас дістається наступному клієнтові,
  і ним може бути Grafana. `SET LOCAL` помирає разом із транзакцією, що б не
  сталося зі з'єднанням далі.
* Пул замінений **одним** `pg.Client`. Пул роздає той бекенд, який вільний, тож пін
  довелося б повторювати на кожному з'єднанні, яке він колись відкриє; з одним
  клієнтом з'єднання одне, і налаштування воно несе за побудовою.
* Рядок `li.dash_config.as_of` лишився як ручний override останньої інстанції —
  лише для власника — і в нормальній роботі він `NULL`: **ніщо в `db/` його більше
  не пише**, жодна CI-роль не має на нього `UPDATE`, а `export.mjs` друкує
  `::warning::`, якщо застане його не-`NULL`.

Доведено (`db/test-roles.mjs`, розділ про годинник, і руками):

```
pinned session (as li_sync): current_month 2031-03-01, current_week_monday 2031-02-24, posts_per_month runs to 2031-03
an independent grafana_ro session, WHILE the pin is held, sees posts_per_month end at the real month (2026-09)
an independent owner session, WHILE the pin is held, sees li.as_of() = now()
li.dash_config.as_of is NULL while an export is pinned
after verify.mjs: li.dash_config.as_of is NULL
```

Паритет при цьому байт-в-байт у трьох режимах: на запіненому інстанті, з
`--now <поточний час>`, і **зовсім без піна** (`export.mjs` без `--now` проти
`build-stats-json.mjs` без `--now`).

Тому ж скрипту доданий `--skill-dir`: `scoring.json` і `vip-people.md` були
прибиті до кореня репозиторію, і без цього флага ICP/VIP-гілку скорингу неможливо
перевірити на фікстурі взагалі.

Перевірено, що `--now` не декоративний:

```
build-stats-json --now 2026-09-20  ->  posts_per_month=45  comments_per_month=2
build-stats-json --now 2027-03-01  ->  posts_per_month=51  comments_per_month=8
build-stats-json --now 2026-09-09  ->  last_week = 2026-08-24 (а не 2026-09-07)
```

Паритет тримається на кожному з цих інстантів.

## Гейт публікації

`li.week_publication(author, week, run_id, status)`, де статус —
`pending | published | rejected | superseded`. Уся сила в частковому унікальному
індексі:

```sql
create unique index week_publication_one_published
  on li.week_publication (author, week) where status = 'published';
```

Скільки завгодно `pending`/`rejected`/`superseded` рядків на один
`(author, week)`; **рівно один** `published`. Другий `published` відбиває база, а
не код застосунку.

### Хто публікує: `li.publish_run(run_id, decided_by)`

Під `--publish` імпортер робив прямий
`update li.week_publication set status='published' where status='pending'` — це
вимагало власника і публікувало **всі** `pending`-рядки в таблиці, хто б їх не
подав. Тепер це `SECURITY DEFINER`-функція, видана `li_sync` (і **не** `li_writer`:
скрейпер просить, а не вирішує). Вона працює лише з одним прогоном:

1. **Перевидання.** Якщо цей прогін переписав рядок знімка (`post_week`,
   `account_week`, `comment_week` — `replace_*`-функції ставлять `run_id` рівно на
   ті рядки, які змінили) у тижні, що вже опублікований *іншим* прогоном, — числа,
   які показує Grafana, вже не ті, що публікувались. Для такого тижня подається
   `pending`-рядок цього прогону. Повтор без змін нічого не штампує — в усталеному
   стані тут нуль записів. (Зміна лише в дітях знімка — демографія, ростери —
   батька не штампує і публікацію не перевидає; дані лягають, аудит-рядок лишається
   за старим прогоном.)
2. **`superseded`** — опублікований рядок кожного тижня, на який цей прогін має
   `pending`. Саме **перед** промоцією: частковий унікальний індекс перевіряється
   на кожній команді, тож «рівно один `published`» тримається в кожен момент.
3. **`published`** — `pending`-рядки цього прогону, і тільки вони.

`li.request_week(…, p_takeover => true)` — парна деталь. Знімок замінюється на місці
тим прогоном, який імпортував останнім, тож чужий старий `pending`-запит описує
дані, яких у такому вигляді вже немає. Прогін, який збирається публікувати,
позначає такий запит `superseded` і подає свій — інакше сценарій «імпорт → подивитись →
імпорт `--publish`» лишав би тижні першого прогону `pending` назавжди. За
замовчуванням вимкнено, щоб прогін без публікації лишався строго ідемпотентним.
**Опублікований** тиждень `p_takeover` не чіпає ніколи.

Писар **не має `INSERT` на цю таблицю взагалі**. Єдині двері — `SECURITY DEFINER`
функція `li.request_week()`, у якій статус захардкожений у `pending`. Просто
відібрати `UPDATE` було б замало: з `INSERT` на таблиці писар вставив би рядок,
у якому одразу написано `published`, і обійшов би гейт, не торкаючись `UPDATE`.
Перевірено: `insert ... status='published'` від `li_writer` → `permission denied`,
`li.request_week()` → `pending`, `update ... set status='published'` →
`permission denied`.

Кожна в'юха в `dash`, що має колонку `week`, інner-джойниться до
`dash.published_week`. Рядки без власного тижня (пости, люди, події, таргети)
тримає окрема колонка:

| рядок | чим загейчений |
|---|---|
| `li.post` | має опублікований `post_week` — **або** не має жодного знімка взагалі (37 із 126 постів Петра; це корпус, не вимір) |
| `li.comment` | так само |
| `li.person.gate_week` | понеділок тижня `first_seen_at` |
| `li.engagement_event.gate_week` | понеділок тижня `first_seen_at` — **не** `attributed_week` |
| `li.scan_target` | `first_scanned_week` (це вже тиждень скрапу) |

Чому подія гейчиться за `first_seen_at`, а не за `attributed_week`:
`attributed_week` сягає `2023-03-27` — це коли енгейджмент **стався**. Гейт же
про те, коли **прогнався скрап**. Гейтити за `attributed_week` означало б
вимагати рядок публікації за кожен тиждень із 2023 року.

Дані сторінки компанії (`li.page_*`) **не** за гейтом: це місячний XLS-експорт,
там нема щотижневого скрапу, який можна публікувати.

## Merge-правила

Це не звичайні апсерти, і саме їх найлегше зіпсувати. Кожне звірене з
`merge.py` — рядок, на який спирається реалізація, процитований у `COMMENT ON`
функції або колонки в `schema.sql`. Правил три **види**, і плутанина між ними —
основний спосіб зламати цей шар.

**1. APPEND-ONLY — події енгейджменту.** `ON CONFLICT DO NOTHING`, ніколи
`DO UPDATE`. `merge.py:272` → `if event_id in events: continue`. Перезапущений
(або вбитий і відтворений) прогін не має права передатувати чи здублювати
енгейджмент.

**2. ЗАМОРОЖЕНЕ ПОЛЕ — `person.first_seen_at` і
`scan_target.first_scanned_week`.** `merge.py:244-254` виставляє перше тільки в
гілці `entry is None`; `merge.py:315` проти `320-322` — те саме для другого.
Решта рядка перезаписується. Плюс «ніколи не затирати відоме значення порожнім»
(`merge.py:259-261`) — оверлей реакцій інколи малює людину без хедлайна.

`first_scanned_week` і `last_scanned_week` передаються **окремими масивами**: у
сьогоднішньому корпусі 8 таргетів мають їх різними вже на першому імпорті, і
злиття в одну колонку переписало б заморожений факт одразу.

**3. ЗАМІНА — тижневий знімок і кожен документ, який скрапер перезаписує цілком.**
`merge.py:84` і `merge.py:96` — це `data.setdefault("weeks", {})[week] = snapshot`,
звичайне присвоєння. Тобто **повторний скрап тижня перезаписує його**, разом із
демографією, коментарями й ростерами, які приїхали всередині знімка. Те саме
стосується кеша профілів (`profile-store.mjs:300-353`), місячного експорту
сторінки (`monthly.json` перезаписується парсером цілком — про це сказано в
`manual.json._note`) і конфігу скорингу (`scoring.json` сам про себе каже, що
редагування «rescores all history on the next build»).

Це найважливіше з трьох: якби знімки лишилися insert-only, часткові тижні
(наприклад, фаза `--phases=people` кладе `{snapshot_at, people_only:true}` без
метрик, а фаза метрик дописує числа) назавжди залишилися б у базі порожніми, а
JSON-фід показував би виправлені. Перевірено обидва напрямки — див. експерименти.

Правила 2 і 3 вимагають `UPDATE`/`DELETE`, а роль `li_writer` їх не має. Тому
вони живуть у `SECURITY DEFINER`-функціях, якими володіє `li_owner`:
`li.upsert_post`, `li.replace_post_week`, `li.replace_account_week`,
`li.upsert_comment`, `li.replace_comment_week`, `li.upsert_person`,
`li.set_person_icp`, `li.upsert_scan_target`, `li.upsert_profile`,
`li.request_week`, `li.publish_run`. Правило написане один раз, його видно в одному місці, і писар
не може дотягнутися повз нього до `UPDATE` чогось іншого.

Конфіг і документ сторінки компанії (`li.upsert_author`, `li.set_scoring`,
`li.set_vip`, `li.replace_page`) **скрейперові** (`li_writer`) не видані взагалі: це
вхідні дані оператора й місячний XLS, не результат скрапу. Їх виконує імпортер —
від імені власника або `li_sync`.

### Пастка з батчем, і в який бік його згортати

`INSERT ... ON CONFLICT DO UPDATE` не може зачепити один рядок двічі в одній
команді. `merge.py` це сходить з рук лише тому, що він будує пітонівські дікти.
Але **напрямок згортання не «останній виграє»** — і саме тут легко зробити гірше,
ніж було:

| батч | `merge.py` | як тут |
|---|---|---|
| двічі та сама подія | перша виграє (`merge.py:271-273`) | не згортається взагалі — `DO NOTHING` лишає першу |
| двічі та сама людина | перший запис засіває, далі тільки **непорожні** поля | `foldPeople()` |
| двічі той самий таргет | перший задає `first_scanned_week`, далі рухаються `last_*` і `reactor_count` | `foldTargets()` |

Згортання «останній виграє» для подій передатувало б енгейджмент, а для таргетів
розморозило б `first_scanned_week`. Обидва випадки відтворені й зафіксовані в
`db/test-merge-rules.mjs` — очікувані значення там узяті з фактичного прогону
`merge.py` на батчі з дублікатом.

**Чому `nullif()` на гілці `INSERT` у `li.upsert_person` було б помилкою.**
Спокуса є: тоді порожній хедлайн у першому записі не потрапив би в базу. Але
`merge.py:243-254` кладе значення дослівно, порожні включно, і корпус це
підтверджує: у Петра є `in/johanevj` з `name: ""` і `headline: ""`, а рідер
(`build-stats-json.mjs:356`, `person?.name ?? key`) залишає порожній рядок, а не
підставляє ключ. З `nullif()` база віддала б `in/johanevj` замість `""` і паритет
зламався б. Правильна відповідь — згортання батча, а не `nullif`.

## Ролі

```sql
-- створені БЕЗ паролів; паролі ставить оператор, і їм не місце в репозиторії
ALTER ROLE li_writer  WITH LOGIN PASSWORD '...';
ALTER ROLE grafana_ro WITH LOGIN PASSWORD '...';
ALTER ROLE li_sync    WITH LOGIN PASSWORD '...';
ALTER ROLE li_backup  WITH LOGIN PASSWORD '...';
```

Поки пароля нема, роль не автентифікується по мережі — саме та поведінка за
замовчуванням, якої хочеться від файлу, що лежить у git.

| роль | що може |
|---|---|
| `li_owner` | `NOLOGIN`. Володіє обома схемами, усіма таблицями, в'юхами й функціями. Існує для того, щоб тіло `SECURITY DEFINER` **не виконувалося від суперкористувача**. |
| `li_writer` | скрейпер. `USAGE` на `li`, `SELECT` + `INSERT` на таблиці `li` (окрім `li.week_publication`), `EXECUTE` на merge-функції. Без `UPDATE`, `DELETE`, `TRUNCATE`; без `li.publish_run` і без конфіг-функцій. |
| `grafana_ro` | `USAGE` на `dash`, `SELECT` на в'юхи `dash`. `li` не бачить узагалі. |
| `li_sync` | **CI, dual-write.** `SELECT` на `li` і `dash` (для `verify.mjs`); `INSERT` рівно на дві таблиці, куди імпортер дописує сам (`li.import_run`, `li.engagement_event`); `EXECUTE` на всі merge-функції, на документи конфігу/сторінки (`upsert_author`, `set_scoring`, `set_vip`, `replace_page`), на `request_week` і `publish_run`. **Жодного** `UPDATE`/`DELETE`/`TRUNCATE`/DDL — кожне правило, якому вони потрібні, є definer-функцією. |
| `li_backup` | **CI, дамп.** `USAGE` + `SELECT` на всі таблиці, в'юхи й послідовності `li` і `dash` — рівно те, що читає `pg_dump` (включно з `last_value` послідовності). Жодного запису, жодного `EXECUTE` на функції, що пишуть. |

Default privileges покривають майбутні таблиці: `li_backup` і `li_sync` отримають на
них `SELECT` автоматично. `INSERT` для `li_sync` — **навмисно ні**: нова таблиця, куди
імпортер мусить писати напряму, потребує явного гранту, і `test-roles.mjs` (він
запускає справжній імпортер від `li_sync`) падатиме гучно, доки хтось не вирішить
це свідомо.

### `db/test-roles.mjs` — перевірка дією

Ролі приміряються двома способами, і README каже, яким саме прогнано:

* **справжній вхід** (`--sync-dsn`/`LI_SYNC_DSN` тощо). Локально для цього ролям
  руками ставляться одноразові паролі (`alter role li_sync password '…'` у
  контейнері `li-pg` — у `schema.sql` їх немає й не буде). Це ближче до бойового:
  і `current_user`, і `session_user` — сама роль; з'єднання з хоста йде через
  scram, а не `trust`; і лише так має сенс перевірка «`li_sync` не може
  `SET ROLE li_owner`».
* **`SET ROLE`** від імені власника — без жодних DSN, для швидкого локального
  прогону суперкористувачем. Для імпортера (окремий процес) `SET ROLE` їде в DSN як
  `options=-c role=li_sync`. Привілеї перевіряються за `current_user`, тож відмови
  ті самі; не-суперкористувач-власник так не вміє (з PG16 ADMIN OPTION не дає
  `SET ROLE`), і тоді потрібні DSN.

Обидва режими зелені. Основний прогін — справжнім входом, і власник у ньому —
**не суперкористувач** (`CREATEROLE` + `CREATEDB`, як `postgres` на Supabase), що
володіє власною базою: так само перевірено, що `schema.sql` накочується такою роллю.

Частина A — на базі з `--dsn`, нічого не змінюючи: що кожна роль читає і в чому їй
відмовлено (відмова зараховується лише з кодом `42501`, а не будь-яка помилка).
Частина B — у тимчасовій базі: `import.mjs --publish` від `li_sync` на **порожній**
базі, повторно (0 рядків), на виправленому корпусі (рівно 3 рядки: знімок,
`superseded`, `published`), `verify.mjs` тією ж роллю, `--reset` → відмова, семантика
`publish_run`/`p_takeover`, і всі відмови ще раз — там, де `li_sync` щойно справді писав.

`CREATE FUNCTION` роздає `EXECUTE` на `PUBLIC` за замовчуванням. На
`SECURITY DEFINER`-функції це означає, що будь-яка роль із самим лише `USAGE` на
схемі `li` — грант, який легко видають аналітику чи міграційному інструменту, —
могла б переписати `li.person`, не маючи жодного права на таблиці. Тому схема
явно робить `revoke execute ... from public` на кожну функцію `li`, а власником
робить `li_owner`, а не `postgres`. Перевірено: роль із `USAGE` і без табличних
прав дістає `permission denied for function upsert_person`.

Наслідок, який варто назвати вголос: **опублікувати тиждень — це рішення, не
запис.** Скрейпер може тільки попросити (`li.request_week()` → `pending`). Публікує
власник — або `li_sync`, і лише те, що він сам щойно відтворив із `main`, де
рішення вже ухвалене мерджем PR.

## Резервна копія і навчальне відновлення

На безкоштовному тарифі Supabase резервних копій немає, тож копію знімає CI.

```bash
LI_BACKUP_DSN=<dsn ролі li_backup> db/backup.sh <out.sql>
```

`pg_dump --schema=li --schema=dash --no-owner --no-privileges`, звичайний SQL.
DSN — лише з env: `pg-env.mjs` розбирає його тією ж бібліотекою, що й решта `db/`,
і передає `psql`/`pg_dump` частинами через `PG*`-змінні, яких не видно в `ps`
(`pg_dump "$DSN"` світив би пароль усім на машині). Для хостів `*.supabase.com` —
`PGSSLMODE=verify-full` і `PGSSLROOTCERT=db/certs/supabase-root-2021.crt`: і ланцюг,
і ім'я хоста. `sslmode=require` у libpq сертифікат **не перевіряє взагалі**.

* **`pg_dump` не молодший за сервер.** Бойовий сервер — 17, на `ubuntu-latest`
  клієнт 16. Скрипт порівнює мажорні версії наперед і каже, що ставити
  (`postgresql-client-17`), код `3`.
* **У лог — лише лічильники.** Таблиця → рядків у дампі → рядків у базі, розмір,
  sha256. Кількість рахується **з самого файла** (рядки між `COPY … FROM stdin;` і
  `\.`): твердження «у копії N рядків» має бути про копію, а не про базу.
* **Тихий нуль — не копія.** Дамп без жодного `li.account_week` (база скинута або
  прокинулась порожньою) — код `5`, файл не створюється. Розбіжність дампа з
  базою — теж `5`.
* Файл пишеться з `umask 077` у сусідній `.partial` і перейменовується наприкінці:
  обірваний дамп ніколи не лежить під іменем справжнього. **Сам файл — це весь
  корпус**: йому місце в приватному репозиторії, і ніколи — в артефактах публічного
  прогону. `db/.gitignore` про всяк випадок ігнорує всі `*.sql`, крім `schema.sql`.

Копія, яку ніхто не відновлював, — не копія:

```bash
LI_DRILL_DSN=<сервер, де можна створити базу — НЕ бойовий> \
LI_BACKUP_DSN=<джерело> db/restore-drill.sh <dump.sql> [--verify] [--keep]
```

Створює тимчасову базу, відновлює дамп через `psql` з `ON_ERROR_STOP`, порівнює
кількість рядків у кожній таблиці з джерелом, кількість в'юх і функцій, **читає
кожну `dash`-в'юху** (схема, яка відновилась, але не виконується, — теж не
відновлення), і видаляє базу. `--verify` додатково проганяє `verify.mjs` **проти
відновленої бази** — найсильніше з тверджень: з цієї копії збираються ті самі
дашборди байт-в-байт. Сервер відновлення має бути не старший за `pg_dump`, яким
знято копію (дамп від 17-го клієнта містить `SET transaction_timeout`).

Локально `psql`/`pg_dump` немає — `db/docker-bin/` підміняє їх викликом у контейнер
`li-pg`, ходячи на базу через `host.docker.internal`, тобто зі справжньою
автентифікацією (усередині контейнера `127.0.0.1` — це `trust`).

## Що перевірено на реальних даних

Усе нижче прогнано проти локальної бази з повним корпусом.

* **Паритет** — 4 фіди (`peter`, `andy`, `maria`, `page-stats`) байт-в-байт, на
  трьох різних запінених інстантах.
* **Паритет після перескрапу** — копія корпусу з виправленим тижнем поста
  (`impressions 1639 -> 2139`, `engagement_rate 1.1 -> 9.99`), виправленим тижнем
  акаунта (`followers 734 -> 777777`), перерахованою вагою скорингу
  (`normal/comment 5 -> 99`), перевиданим місяцем сторінки
  (`2026-03 page_views 961 -> 100961`) і зміненим файлом кеша профілю. Імпорт
  записав рівно 5 рядків, усі нові значення в базі, **усі 4 фіди знову
  байт-в-байт**. Це тест, який ловить «insert-only знімки».
* **Порядок фаз** — тиждень, створений фазою `people` (`has_metrics=false`,
  `impressions NULL`), після фази метрик став `has_metrics=true`,
  `impressions=4242`.
* **Заміна як множина** — демографічна мітка, що зникла з нового знімка
  (`company_size / 51-200 employees`), зникла з таблиці, нова
  (`1-10 employees = 100`) з'явилася. Не об'єднання, а заміна.
* **Ідемпотентність** — другий імпорт по тих самих даних: `0 row(s) written` у
  кожній таблиці. Те саме на фікстурі, де вердикти ICP існують.
* **Три merge-правила** — `db/test-merge-rules.mjs`, очікувані значення зняті з
  фактичного прогону `merge.py` на батчі з дублікатом. 5/5.
* **ICP / VIP** — `db/fixture-icp.mjs`. На реальному корпусі ця гілка
  **непокрита**: усі 720 профілів мають `icp: null`, а `vip-people.md` порожній,
  тож `is_icp=false` і `tier='normal'` в обох боків, і близько 5% порівняних
  листків збігаються лише тому, що обидва вироджені. Фікстура дає 3 ICP, 2 VIP
  (один із них — випадок `precedence: max`, тобто і VIP, і ICP) і 2 відхилені
  вердикти; у фіді `score_icp=20`, `score_vip=120`, `people_icp=4`,
  тижневі `score_icp>0` — і паритет байт-в-байт.
* **Годинник не тече** — поки одна сесія тримає пін на 2031 рік, незалежна сесія
  `grafana_ro` бачить справжній місяць; після `export`/`verify` рядок
  `li.dash_config.as_of` — `NULL`. Паритет байт-в-байт на запіненому інстанті, на
  поточному часі й зовсім без піна.
* **Dual-write від `li_sync`** — справжнім входом, власник — не суперкористувач:
  перший синк на порожній базі (8313 рядків, 9 тижнів опубліковано, 0 `pending`),
  повтор — `-- 0 rows written`, перескраплений тиждень — рівно 3 рядки й перевидана
  публікація, `verify.mjs` тією ж роллю — байт-в-байт, `--reset` — відмова з кодом 2.
* **Резервна копія** — `backup.sh` від `li_backup` (29 таблиць, 8306 рядків, 30 в'юх,
  21 функція), `restore-drill.sh --verify`: усі таблиці збіглися з джерелом, усі
  30 в'юх виконуються, паритет відновленої бази з JSON — байт-в-байт. Відмови:
  неправильний пароль і недосяжний хост → `4` (хост і користувач вирізані з
  повідомлення), `pg_dump` 15 проти сервера 16 → `3`, порожня база → `5`.
* **Лог без значень** — ім'я людини на місці дати дає
  `SQLSTATE 22007 · in upsert_post — invalid input syntax for type date: <value withheld>`;
  обрізаний файл профілю — `dashboards/profiles/<file sha1:…>: not valid JSON`.
* **Гейт** — `li_writer` не може ні вставити `published`, ні перевести `pending`
  у `published`; `li.request_week()` дає рівно `pending`; другий `published`
  відбиває індекс.
* **Ролі** — роль із самим `USAGE` на `li` дістає `permission denied for function`
  на всі три definer-функції (раніше вона могла переписати `li.person`).
* **Зіпсований вхід** — `peter/account.json`, обрізаний навпіл (реалістичний crash
  mid-write), валить імпорт із кодом 1 і нічого не комітить. Валідний, але
  порожній `{"weeks":{}}` теж валить: автор, у якого є тижні постів і нуль тижнів
  акаунта, — це половина корпусу, а не корпус.
* **Редакція діфа** — примусово зламаний паритет (489 змінених хедлайнів) друкує
  шлях + `тип/довжина/sha1`, і жодного тексту.

## Відоме, ще не зроблене

* **Немає недеструктивної міграції.** `schema.sql` дропає обидві схеми; на етапі
  dual-write це прийнятно (база — похідна копія JSON), але щойно база стане
  джерелом правди, потрібні будуть справжні міграції.
* **TLS у `backup.sh` локально не перевірити**: у контейнері немає TLS. Перевірено
  лише, що для хоста `*.supabase.com` `pg-env.mjs` виставляє
  `PGSSLMODE=verify-full` і `PGSSLROOTCERT` на закріплений корінь; перший справжній
  прогін — на боці оператора.
* **Перевидання публікації бачить лише рядок знімка** (див. `li.publish_run`, п. 1).
* **Те, що ВИДАЛИЛИ з `main`, лишається в базі.** Імпортер лише зливає: пост, тиждень
  чи файл, який прибрали з git (як чистка «все до листопада 2025», #43), `li_sync`
  з бази не прибере — `DELETE` у нього немає, і це навмисно. Тихо це не минає:
  перевірено на копії корпусу без одного файла поста — синк пише `-- 0 rows written`,
  а `verify.mjs` виходить з `1` (`DIFF maria/stats.json 40 difference(s)`), тобто в
  Slack іде розбіжність паритету. Лікує це тільки власник:
  `node db/import.mjs --reset --publish` (перевірено: після нього паритет знову
  байт-в-байт). Поки база — похідна копія JSON, це прийнятно; коли стане джерелом
  правди, видалення мусить стати явною операцією.
* **Postgres 17 локально не перевірено.** Локальний контейнер і одноразовий «чистий»
  кластер, на якому все прогнано, — 16.14 (образу 17 на машині немає, а тягнути
  його без дозволу не став). Бойовий сервер — 17.6: нічого специфічного для 16 у
  `schema.sql` немає, але перший справжній `apply-schema` / `backup.sh` з клієнтом 17 —
  на боці оператора. Гілку «`pg_dump` молодший за сервер» перевірено підставним
  `pg_dump 15` проти сервера 16.

* **Per-person engagement сторінки компанії.** `build-page-stats.mjs` має гілку
  для `dashboards/li-stats/page/engagement.json`, але цього файла ніколи не
  існувало, тож секція віддає літеральні `"???"` — і `export.mjs` відтворює
  саме це. Коли файл з'явиться, йому потрібен власний author-скоуп у `li`.
* **`li.account_week.raw`.** Типізовані колонки покривають те, що читають
  дашборди сьогодні; решта блоків знімка (`clicks_per_section`,
  `where_appeared`, `top_companies_pct`, `highlights`) лежить у `raw jsonb`.
  Нічого не втрачено — знімок збережений дослівно, — але підняти блок у колонки
  доведеться, коли на нього з'явиться панель.
* **Пости без жодного тижневого знімка** проходять гейт як корпус. Якщо колись
  стане важливо ховати навіть факт існування такого поста до публікації, потрібна
  колонка `discovered_week` на `li.post`, яку нинішній JSON-корпус дати не може.
* **Місяць, що зник із `monthly.json`, лишається в базі.** Заміна робиться для
  тих ключів, які документ стверджує; рядок, якого в новому експорті немає,
  вважається історією. Якщо LinkedIn колись *прибере* місяць свідомо, це треба
  буде робити руками.
