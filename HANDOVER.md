# Передача справ: як прийняти LinkedInStatistic

Два читачі: **той, хто йде** (чекліст у §6), і **той, хто приймає**
(решта документа). У файлі лише назви, ніколи не значення: тут не місце для
ключів, DSN, токенів чи Slack ID, бо репозиторій публічний.

## 1. Що де працює

Усе, що за розкладом, працює в GitHub Actions. Сервера немає, ні на чиїй машині
немає cron чи launchd-завдань, а CI не потрібен жоден Claude/Anthropic-ключ
(`.claude/skills/` лише для інтерактивної роботи локально).

| Що | Коли | Workflow |
|---|---|---|
| Зібрати кожного активного автора, відкрити PR | пн 00:00 UTC | `linkedin-stats-weekly.yml` |
| Перевірка сесій (чи живі логіни LinkedIn) і keep-alive бази | щодня 07:00 UTC | `linkedin-session-check.yml` |
| Публікація на Pages, синк у Postgres, бекап | після змерджженого тижня або вручну | `pages-deploy.yml` |

Keep-alive важливий: керований Postgres присипляє неактивні проєкти, а щоденна
перевірка сесій якраз не дає йому заснути. Цей workflow вимикати не можна.

Склад авторів (`.claude/skills/linkedin-stats/profiles.json`): сьогодні збирається
один автор; двоє `retired` (їхні дані й дашборди лишаються, але їх більше не
відвідують). Ще один slug лежить у реєстрі логінів без самого логіна.

## 2. Що є лише на машині того, хто йде

Цього немає в git, і **з GitHub це не прочитати** (секрети тільки пишуться).

| Файл | Що в ньому | Якщо загубити |
|---|---|---|
| `scripts/lifleet/authors.json` | реєстр: slug автора → Browserbase `context_id` | копія є в секреті `LIFLEET_AUTHORS_JSON`, але читає її лише CI. Втратиш обидва, і кожному автору доведеться логінитись наново |
| `scripts/lifleet/.env` | ключ Browserbase API, id проєкту, регіон | видати новий ключ у дашборді Browserbase |
| `.env` (корінь репозиторію) | адреса й токен Grafana, uid папки й джерела, DSN бази, `LI_OPT_OUT` | новий токен сервісного акаунта Grafana; паролі ролей бази з боку Supabase (`db/README.md`) |

Форми файлів: `.env.example`, `scripts/lifleet/.env.example`,
`scripts/lifleet/authors.example.json` (значення в них навмисно фальшиві).

Передавай їх через менеджер паролів, не месенджером і не поштою. А ще краще:
видай наступнику **власний** сервісний акаунт Grafana і **власний** ключ
Browserbase, а старі відклич. Тоді витік коштує один ключ, а не весь сетап.

## 3. Акаунти й хто ними володіє

З репозиторію власника не видно. **Заповни останню колонку до передачі**;
усе, що висить на особистому акаунті, треба перенести або створити заново.

| Сервіс | Навіщо | Назви (секрет CI / змінна) | Власник |
|---|---|---|---|
| Репозиторій GitHub | код, Actions, Pages, секрети | кілька адмінів; `GITHUB_TOKEN` видається автоматично | |
| Browserbase | віддалений браузер; тримає залогінену сесію LinkedIn кожного автора | `BROWSERBASE_API_KEY`, `BROWSERBASE_PROJECT_ID`, `LIFLEET_AUTHORS_JSON` | |
| Supabase (Postgres) | проєкт `linkedin-stats`, регіон `eu-central-1` | `LI_SYNC_DATABASE_URL`, `LI_BACKUP_DATABASE_URL` | |
| Grafana | дашборди, що читають Postgres | `GRAFANA_SERVICE_ACCOUNT_TOKEN`, змінна `GRAFANA_URL` | |
| Slack-застосунок | щотижневий звіт, алерти про сесії, канал `#linkedin-session-bot` | `SLACK_BOT_TOKEN`, змінна `SLACK_CHANNEL_ID`, `SLACK_PEOPLE_JSON` | |
| Бекапи | дампи, що пушаться в приватний репозиторій бекапів | `LI_BACKUP_DEPLOY_KEY` (див. «Резервна копія» в `db/README.md`) | |

LinkedIn-акаунти належать людям, яких відстежуємо. Їхні логіни живуть як cookies
у Browserbase, і оновити їх можуть лише вони самі (пароль і 2FA) через
live-view лінк, який дає `lifleet invite <slug>`.

## 4. Кого пінгує бот

`SLACK_PEOPLE_JSON` зіставляє імена зі Slack member ID. Тегається лише запис
`_operator`, і лише коли прогін упав або вийшов неповним. Авторів не тегають
ніколи. **Він має вказувати на чинного оператора**, інакше про збої дізнається
людина, яка вже їх не читає. Що з двох, секрет чи змінна з такою назвою, є
головним: `WEEKLY-CADENCE.md` §2.

## 5. Регулярні обов'язки

- **Чистий понеділок:** нічого робити не треба. PR змерджиться сам і опублікується.
- **Нечистий** (автор partial, rate-limited, розлогінений, …): дані чекають у
  відкритому PR, а оператора тегають у Slack. Переглянь PR, змерджи, потім
  опублікуй: `gh workflow run pages-deploy.yml --repo speedandfunction/LinkedInStatistic --ref main`.
  Як читати прогін: `WEEKLY-CADENCE.md` §8.
- **Логін LinkedIn помер:** щоденна перевірка постить лінк на повторний вхід,
  автор логіниться. Процедура відновлення: §6 у `WEEKLY-CADENCE.md`.
- **Додати або вивести автора:** §5 у `WEEKLY-CADENCE.md` і абзац «Retiring a
  person». Зміну в `profiles.json` треба влити в `main` **до** того, як чіпати
  секрет реєстру, інакше preflight завалить увесь прогін.

## 6. Чекліст для того, хто йде

- [ ] Наступник має write-доступ до репозиторію й право запускати workflows.
- [ ] Три локальні файли з §2 передані; наступник запустив `lifleet list` із
      `scripts/lifleet/` і бачить ті самі slug авторів.
- [ ] У наступника **власні** ключ Browserbase і токен сервісного акаунта
      Grafana; твої відкликані.
- [ ] Колонка «Власник» у §3 заповнена, і нічого важливого не висить на
      особистому акаунті.
- [ ] `_operator` у `SLACK_PEOPLE_JSON` — Slack ID наступника.
- [ ] Наступник запустив один прогін вручну (`WEEKLY-CADENCE.md` §7) і прочитав
      результат (§8).

## 7. Як підняти машину

Кроки встановлення, чотири перевірки лише на читання, що доводять правильність
сетапу (реєстр, паритет бази, кожна панель Grafana, токен Grafana), і список
файлів: `.claude/skills/linkedin-stats/MOVING-MACHINES.md`, §2 і §3.
